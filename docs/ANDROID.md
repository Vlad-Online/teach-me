# teach-me для Android + синхронизация с десктопом

Статус: решения приняты (синхронизация встроенная по локальной сети; распознавание — системное Android + OpenAI).

## 1. Что хотим

- Тот же тренажёр на телефоне: клип → перевод голосом → вторая попытка с субтитрами → разбор.
- Телефон работает **сам по себе**: офлайн проигрывает клипы, ведёт свои повторения.
- **Синхронизация** с десктопом встроенная: устройства сами находят друг друга в одной сети, без сторонних программ и облаков:
  - новые фразы и клипы, собранные на ПК, появляются на телефоне;
  - прогресс общий: фраза, выученная на телефоне, не всплывёт на ПК как новая.

Сборщик базы (yt-dlp + ffmpeg) остаётся только на ПК: на телефоне ему не место.

## 2. Приложение: Tauri 2 Mobile

Tauri 2 собирает Android-приложение из того же Rust-кода и того же HTML-интерфейса.

| Часть | Десктоп | Android |
|---|---|---|
| Ядро: SQLite, FSRS, проверка ответов, Claude/OpenAI | `crates/core` | тот же `crates/core` |
| Интерфейс карточки | `ui/index.html` | тот же файл, вёрстка под телефон |
| Видео | `<video>` в WebView2 | `<video>` в Android WebView |
| Напоминания | таймер в трее | уведомление по расписанию (WorkManager, Kotlin-плагин) |
| Голос | `Ctrl+Space` + cpal → OpenAI | большая кнопка «держи и говори» |
| Распознавание речи | OpenAI `gpt-4o-mini-transcribe` | **системное Android SpeechRecognizer** (бесплатно, работает офлайн), OpenAI — запасной вариант |

Почему не нативный Kotlin: пришлось бы второй раз писать FSRS, проверку ответов, клиентов API и интерфейс.
С Tauri общий код — около 80%, на Kotlin пишутся только два маленьких плагина: напоминания и распознавание речи.

Изменения в ядре:
- `reqwest` на `rustls` вместо системного TLS (на Android нет schannel);
- ключи API на телефоне вводятся один раз в настройках (или сканированием QR-кода с ПК), в репозиторий синхронизации **никогда** не попадают.

Как работает на телефоне:
- уведомление «Новая фраза» в активные часы раз в N минут (WorkManager, минимум 15 мин);
- тап по уведомлению → сразу карточка;
- без сети: клип играет, распознавание системное, проверка — точное совпадение с эталоном
  или кнопки «я ответил верно / неверно»; результат попадает в журнал и уйдёт при следующей синхронизации.

## 3. Синхронизация: встроенная, по локальной сети

Решение: **никаких сторонних программ и облаков**. Приложения сами находят друг друга, когда ПК и телефон
в одной сети (дома по Wi-Fi), и синхронизируются. Вне общей сети каждое устройство работает само
и копит свой журнал; при следующей встрече всё сливается.

### Роли

- **ПК — сервер.** Программа в трее и так работает постоянно; в ней живёт маленький HTTP-сервер
  (`tiny_http`, без асинхронного рантайма) и отвечающий на поиск UDP-сокет.
- **Телефон — клиент.** Начинает синхронизацию сам: при запуске, после каждой карточки (с задержкой, пачкой),
  по кнопке и в фоне при уведомлении.

### Обнаружение

1. Телефон шлёт широковещательный UDP-пакет `teach-me? <id телефона>` на порт 47811
   (255.255.255.255 и broadcast-адрес своей Wi-Fi подсети).
2. ПК отвечает **адресно** (unicast): `teach-me! <id ПК> <порт HTTP>`.
3. Телефон запоминает адрес ПК и в следующий раз сначала пробует его напрямую.

Почему так, а не mDNS: на Android приём multicast/broadcast требует `MulticastLock` и часто режется
в фоне, а отправка broadcast и приём unicast-ответа работают без ограничений. Запасной путь —
ввести IP ПК вручную в настройках.

### Сопряжение (один раз)

- В трее на ПК пункт «Подключить телефон» показывает QR-код: адрес ПК, порт и **ключ сопряжения**
  (случайные 32 байта).
- Телефон сканирует QR (плагин Tauri barcode-scanner). Ключ хранится в приватном хранилище приложения.
- Каждый запрос телефона идёт с этим ключом (`Authorization: Bearer …`); без него сервер отвечает 401,
  поэтому чужое устройство в той же сети к базе не подключится.
- Там же, по желанию, переезжают ключи Claude/OpenAI — чтобы не вводить их на телефоне руками.

Трафик по локальной сети не шифруется (HTTP). Для домашней сети это приемлемо; если понадобится —
добавим шифрование тем же ключом сопряжения.

### Протокол

| Запрос | Что делает |
|---|---|
| `GET /manifest` | id ПК; все фразы (uid, текст, перевод, разбор); список клипов (файл, uid фразы, размер) |
| `GET /clips/<file>` | файл клипа; телефон качает только те, которых у него нет |
| `POST /sync` | телефон отдаёт свои новые события и «отметки» — до какого времени он знает события каждого устройства; ПК сохраняет события и возвращает те, которых у телефона нет |

Фраз — сотни, манифест весит десятки килобайт; клипы ~75 КБ, первая синхронизация 130 клипов ≈ 10 МБ.

### Как устроено, чтобы не было конфликтов

- **Прогресс — журнал событий**, а не состояние: `{"id", "device", "phrase": "<uid>", "dir", "ts", "outcome", "answer"}`.
  События только добавляются и никогда не меняются; повторно полученное событие игнорируется по `id`.
- **Расписание FSRS = воспроизведение всех событий фразы по времени** (со всех устройств).
  Разброс интервалов в FSRS детерминирован (зависит от времени ответа и состояния карточки),
  поэтому, получив одинаковые события, ПК и телефон вычисляют одинаковое расписание. Это покрыто тестом.
- **Стабильный uid фразы** — хеш нормализованного португальского текста, одинаковый на всех устройствах.
- **Контент создаёт только ПК** (сборщик), телефон его только получает.
- **SQLite не копируется** между устройствами: у каждого своя база, обмен — только событиями и контентом.

### На ПК

- Windows при первом запуске сервера спросит, разрешить ли доступ к сети — разрешить для частных сетей.
- Сервер работает, пока программа в трее запущена; в настройках можно выключить.

## 4. Этапы

1. **Ядро под синхронизацию**: uid фраз, журнал событий вместо прямой записи в `reviews`, пересчёт FSRS из журнала,
   переход на rustls. Миграция текущей базы (126 фраз и уже пройденные карточки сохраняются).
2. **Синхронизация**: модуль `sync` в ядре (сервер на ПК, клиент для телефона, UDP-обнаружение, сопряжение по QR).
   Проверяем двумя копиями программы на ПК: одна в роли телефона.
3. **Android-сборка**: Android Studio/SDK/NDK, Java 17, `rustup target add aarch64-linux-android`,
   `tauri android init`. Карточка и плеер на телефоне, ручная синхронизация.
4. **Плагины на Kotlin**: напоминания (WorkManager + уведомления) и системное распознавание речи.
5. **Удобства**: QR-перенос настроек и ключей, экран статистики.

Риски, которые проверим первыми на этапе 3:
- сборка Android с Windows ARM64: Android Studio и эмулятор на ARM64 Windows поддерживаются не во всех версиях;
  запасной путь — сборка без эмулятора, установка на телефон по USB (adb);
- автозапуск видео со звуком в Android WebView (решается настройкой WebView в плагине).
